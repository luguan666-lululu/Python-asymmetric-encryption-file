# 后量子文件与消息加密工具 · v1.1

一个用 Python 和 PyQt6 编写的离线加密工具，支持文件和文本消息。加密、解密及密钥生成均在本机完成，密文由使用者自行传输；程序不提供在线聊天服务或密钥服务器。

采用 ML-KEM-1024、Classic McEliece-8192128、ML-DSA-87 和 SLH-DSA-SHAKE-256f，结合 AES-256-GCM 与 ChaCha20-Poly1305 处理数据。**后量子算法的使用不等于整个自定义协议已获得安全认证。** 具体假设与已知边界见 [安全模型](SECURITY.md)。

## 功能

- 文件加密与解密：24 MiB 分块处理，大文件采用读盘、密码运算和写盘流水线。
- 消息加密：支持中文、换行和表情，解密结果直接显示在页面中。
- 自动识别文件密文与消息密文，统一在“解密”页处理。
- 可选私钥密码保护，使用 Argon2id 派生密钥。
- 文件名加密、随机填充，以及文件和消息共用的发送/接收顺序检查。

## 获取与运行

Windows 使用者可在 [Releases](https://github.com/luguan666-lululu/Python-asymmetric-encryption-file/releases) 查看可用版本。请核对版本号，v1.1 的安装包以该版本发布附件为准。

源码运行目前验证于 Windows x64、Python 3.14.7。建议使用 Python 3.14 的独立环境；本次没有验证其他系统和 Python 版本。

```powershell
Set-Location .\v1.1
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe "加密程序v1.1.py"
```

源码位于仓库的 `v1.1` 文件夹，以上命令从下载后的仓库根目录开始执行。程序按**当前工作目录**寻找密钥和 `文件——密文`，并保存输出；使用快捷方式时也应核对“起始位置”。目录需要有读写权限。

## 快速开始：Alice 与 Bob 通信

**最重要的规则：输入的是对方名称；该名称对应的私钥属于自己，公钥属于对方。私钥始终留在本机。**

### 1. 各自生成密钥

Alice 在“生成密钥”页输入 `Bob`，得到 `Bob——私钥` 和 `Bob——公钥`。此时两个文件都属于 Alice；名称只是本地文件标签。

Bob 在自己的电脑上输入 `Alice`，得到 `Alice——私钥` 和 `Alice——公钥`，此时两个文件都属于 Bob。

生成时可以选择密码保护。密码区分大小写，支持中文和空格。密码丢失没有恢复机制。**如果选择密码保护后，在任一密码输入框取消，当前程序会提示并保存未加密私钥；取消不等于取消生成。**

### 2. 交换并保存公钥

双方先把刚生成的**自己的公钥**另存备份，再通过可信渠道交换：

- Alice 将自己的公钥发给 Bob；Bob 将收到的文件保存为 `Alice——公钥`。
- Bob 将自己的公钥发给 Alice；Alice 将收到的文件保存为 `Bob——公钥`。
- 用收到的对方公钥替换同名公钥文件，保留本机的私钥文件。不要把私钥发给对方。

交换完成后的目录应是：

| 使用者 | 本机文件 | 实际内容 |
| --- | --- | --- |
| Alice | `Bob——私钥` | Alice 自己的签名及解封装私钥 |
| Alice | `Bob——公钥` | Bob 的公钥 |
| Bob | `Alice——私钥` | Bob 自己的签名及解封装私钥 |
| Bob | `Alice——公钥` | Alice 的公钥 |

第一次交换时应确认公钥确实来自对方。以后更换公钥也要重新核验，不能仅凭文件名信任新文件。建议每个通信对象使用独立生成的一组密钥，避免混淆本地状态。

### 3. 加密文件或消息

Alice 给 Bob 发送内容时，输入对面名称 `Bob`：

- 文件：在“文件加密”页选择文件，点击“加密”。
- 消息：在“消息加密”页输入文字，点击“加密消息”。

两者都输出为当前工作目录的 `文件——密文`。已有同名密文时会询问覆盖。**确认覆盖后旧文件可能立即被覆盖；如果本次操作失败，也不保证找回旧密文。**

每次加密完成后再传输密文。不要把原文件、私钥或私钥密码一起发送。

### 4. 解密

Bob 把收到的密文命名为 `文件——密文`，放在运行目录中，在“解密”页输入 `Alice`，点击“解密”。

- 文件密文：恢复文件名并输出文件；遇到同名目标时按提示处理。
- 消息密文：文字显示在解密页面。

反方向通信时，双方同样使用自己目录中的对应名称。

## 顺序检查怎么理解

v1.1 在公钥文件和私钥文件的开头保存本地发送/接收状态，密文携带经过认证的前序标记。文件与消息共用同一条发送顺序。

顺序不一致时会提示，使用者可以选择继续。这是异常提醒，**不是严格阻止重放，也不保证发送时间、送达时间或完整送达**。旧密文、漏收、整体乱序，以及崩溃、断电、读写失败或恢复旧备份，都可能使顺序检查混乱。

公私钥文件会随使用更新，因此备份恢复也会恢复旧状态。出现提示时可结合双方实际发送记录判断；即使选择继续，密文仍需通过认证。不要把顺序正常当作“绝对未被重放”的证明。

## 算法与实现

| 用途 | 当前实现 |
| --- | --- |
| 会话秘密 | ML-KEM-1024 与 Classic McEliece-8192128，各独立封装两次 |
| 对称加密 | AES-256-GCM → ChaCha20-Poly1305，嵌套认证加密 |
| 会话认证 | ML-DSA-87 与 SLH-DSA-SHAKE-256f，认证四份共享秘密的摘要 |
| 摘要 | MLDSAMuHasher 与 SHA3-512 |
| 私钥密码派生 | Argon2id：512 MiB、4 次迭代、4 lanes，32 字节随机 salt |
| 私钥加密 | ChaCha20-Poly1305 → Cobblestone256 |
| 文件名与长度混淆 | 加密文件名、固定文件名槽及小于 3 MiB 的随机尾部填充 |

AES 密钥由第一组两种 KEM 共享秘密异或得到，ChaCha 密钥由第二组异或得到；nonce 初值取自 SHA3-512 摘要，随认证记录递增。记录序号作为 AAD。正文、长度字段、顺序标记和文件名等受到 AEAD 保护。

**当前版本没有 AES-CBC 数据层，也没有对具体正文再次生成最终数字签名。** 结尾是认证记录；双签名覆盖会话秘密摘要，不能描述为“发送方已签署具体正文”。填充中有直接跳过、未纳入认证的区域。

`cryptography` 负责 ML-KEM、ML-DSA、对称加密和私钥保护；`pqcrypto` 负责 McEliece 与 SLH-DSA；`pathvalidate` 校验文件名；`PyQt6` 提供界面。

## 安全边界

- 要求公钥交换及后续本地密钥绑定可信，程序和终端未被攻击者控制。
- 本轮代码分析及有限测试未找到纯线路攻击下正常解密出此前未发送明文的方法；这不是形式化证明或独立安全审计。
- 允许重放、延迟、丢弃和整体乱序。攻击者也能改变部分填充而不改变明文。
- 随机填充不能保证隐藏精确长度；若攻击者可反复提交并观察解密成功/失败，可探测正文或文件名长度。整个密文格式不应宣称严格 IND-CCA2 安全。
- 无前向保密：接收方两套长期解封装私钥泄漏，可解密录制的历史密文；攻击者还能沿用旧会话签名重新加密新正文，而不需要发送方签名私钥。
- 密码保护不防解锁后的内存读取、恶意程序或屏幕监视；不承诺整个程序严格常数时间或所有秘密副本安全擦除。

详细说明和验证范围见 [SECURITY.md](SECURITY.md)。本项目适合学习、实验与代码研究；未经过独立安全审计，不宜把它作为重要数据的唯一保护手段。
